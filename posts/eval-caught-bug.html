评测体系第一次抓到真 bug：工具调用被执行了两次

2026-11-20 · AgentDesk 开发日志 · 标签：评测 / LangGraph / 幂等性

现象

图级评测任务 two_tool_sequence（用户同时问订单状态和价格，期望工具序列 [get_order_status, get_order_amount]）失败。轨迹断言给出的信息很精确： 实际序列是每个工具各出现两次——['get_order_status', 'get_order_status', 'get_order_amount', 'get_order_amount']。

定位

排除模型层（脚本是固定的两轮工具调用）后，问题锁定在 validate 护栏节点。 它的工作是过滤掉参数来源不合法的工具调用，然后重建一条"只含合法调用"的 AIMessage。 问题出在重建：新消息没有复用原消息的 id。

LangGraph 的 add_messages reducer 语义是：同 id 替换，不同 id 追加。 于是状态里同时存在"原 plan 消息（带全部工具调用）"和"重建后的合法子集消息"， 下游 execute 节点把两条消息的 tool_calls 都执行了——每个工具跑两遍。

为什么没造成事故

第二次执行的 create_ticket 带同样的幂等键，工具层返回 "replayed": true（原工单），没有产生重复副作用。幂等键把一个本可能 重复创建两张工单的事故，降级成了一次无害的重复读。这正是当初给写操作强制幂等的原因。

修复

# 重建时复用原消息 id —— add_messages 原位替换，而非追加
out.append(AIMessage(content=last.content or "", tool_calls=allowed, id=last.id))
# 且无拒绝发生时返回空更新：原消息本就携带全部合法调用
if not rejected:
    return {}
三个层面各留了一道防线：回归任务（two_tool_sequence 断言精确的工具调用序列）、 幂等键（同类错误再次发生时副作用仍被吸收）、文档（节点注释写明 add_messages 的替换语义，防止下一个人再踩）。

这件事改变了我对评测的看法

如果断言只检查"最终回复对不对"，这个 bug 完全不可见——两次执行后回复一样正常。 只有把断言放到轨迹上（谁被调用、被调用几次、参数从哪来），工具层的重复执行才会红。 这也顺带回答了一个常被问的问题："评测体系到底值几个钱？"——它值一次真实的线上事故。
