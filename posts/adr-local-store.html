为什么这个规模我不用 Chroma：一份可以被挑战的存储选型 ADR

2026-11-19 · AgentDesk 设计决策（ADR-0004）· 标签：RAG / 架构决策

tempting 的默认答案

做 RAG 项目，"上个向量数据库"几乎是默认动作，简历上也好看。但我把 Chroma 放进了 "延后"栏，理由写在 ADR-0004 里，欢迎挑战。

约束

  • 知识库 ~3 千段（真实语料子集），单进程全量内存计算绰绰有余
  • 语料需要分钟级重建——评测要求"改了切块策略就重跑"，迁移成本必须接近零
  • 纯 CPU 开发机，Chroma 附带的 onnxruntime 等重依赖纯属负担

决策与代价

先落地本地实现：rank-bm25 + numpy 矩阵 + pickle/jsonl 落盘，检索器对外只暴露 add / retrieve / save / load。代价是简历少一个向量库关键词——补偿方式是 把这份缺失转化为数据：

# 消融评测（27 金标，零 LLM 成本）
bm25    hit@5 = 0.852
dense   hit@5 = 0.852
hybrid  hit@5 = 0.926   # RRF 融合，+7.4pp

"两路各自召回不同形态的失败、融合互补"——这个机理结论比库名值钱。

复活条件（写在 ADR 里，防止变成教条）

知识库 > 5 万段、或多服务共享索引、或需要元数据过滤查询时，引入 Chroma 适配器—— 因为 BM25/向量矩阵已抽象为内部件，迁移只动 add/save/load 三个方法， 并附一份同口径对比评测证明"本地实现与 Chroma 结果一致"后再切换。

选型题的正确姿势不是"选了什么"，而是约束是什么、代价是什么、什么时候换。 这也是我把 ADR 写进项目工程规范的原因：每个决策可追溯、可挑战、可复活。
