当网络持续掐断大文件传输：断点续传 + 完整性校验的落地

2026-11-19 · AgentDesk 开发日志 · 标签：数据管道 / 可靠性

背景

AgentDesk 的知识库与业务库依赖三个真实数据源：Olist 电商数据集（42.6MB）、 Amazon QA 问答集（34.5MB）、政府官网的法规原文。开发环境的网络对大文件传输极不友好： 实测反复出现 Connection was reset，一次 34MB 的下载在 8.7MB 处被掐断。

第一个错误：存在即跳过

最初的下载脚本用"文件存在就跳过"做幂等。重跑时残缺文件被当成"已完成"直接放行， manifest.json 里也少了一条记录。这个 bug 直到构建知识库解析 gzip 失败才暴露。

教训：幂等的判断条件不是"存在"，是"完整且校验通过"。对 gzip 文件，完整性校验 就是把整个流读完（读到最后一个成员），成本远低于事后排查。

第二个正确决定：Range 续传

与其祈祷网络窗口，不如假设"每次传输都可能中断"。下载函数改为：

headers = {"Range": f"bytes={offset}-"} if offset else {}
# 206 → 从 offset 追加；200 → 服务端不支持 Range，从头重来
# 每次失败保留已收到的字节，重试直到 content-length 收齐

实测效果：34.5MB 的 Amazon QA 分 4 段续完（8.7 → 15.7 → 24.6 → 31.9 → 完成）， 每次重置零浪费。顺带把 gzip 完整性校验加进主流程，manifest 记录 sha256 + 许可证 + 抓取日期。

延伸：数据工件的"可追溯"承诺

这个脚本现在是 AgentDesk 数据管道的一部分，配套三条规则：

  • 数据永不进 git（许可合规 + 仓库轻量），用下载脚本 + checksum 固定版本
  • 每个数据集在 data/manifest.json 里留 URL/许可证/日期/sha256
  • 评测永远在临时副本上跑，绝不改写共享数据工件（这条也是被 bug 教出来的）

面试里被问"你的数据是真的吗"，答案不是一句"真实数据集"，而是这一整套可核验的链路。
